# SPEC — distill_jev: a multimodal Jev-like decision model on Gemma 4 E4B
### QLoRA + frozen-base self-distillation + code-generated image decisions

Version: 0.1 (draft)
Date: 2026-09-24
Status: proposal — to be approved before implementation

## 1. Objective

Build a new decision model ("Jev-like", same API and readout as Kev) on top of
**Gemma 4 E4B**, trained **from scratch** (fresh pointer head, fresh LoRA, no Kev
weights) with **QLoRA/Unsloth**, reusing **Kev's training data and method** and
extending it with:

1. **Knowledge retention by construction** — the DuplexCascade-Distill/SDFT trick:
   the frozen original Gemma 4 E4B is the teacher. The student learns the decision
   task with the pointer head while a dense per-token forward-KL keeps the student's
   language distribution inside a small neighbourhood of the frozen base, so the
   base model's knowledge (and the instruct behaviour) does not collapse under
   decision fine-tuning. No RL, no rollouts, no reward model.
2. **Fast** — 4-bit QLoRA and a **prefix-level teacher top-k cache**: the KL term
   only applies to state + instruction tokens, which do not depend on option order
   or augmentation, so the teacher is computed once per record and training runs at
   ~1.1–1.2× the cost of plain SFT instead of ~1.5–2×.
3. **Synthetic breadth** — new decision records generated by **Qwen3.5-9B** (the
   model line Kev-9B's base belongs to) served by the local llama.cpp from
   `/mnt/f/GGUF/Qwen_3.5-9B` (UD-Q4_K_XL GGUF, 6.1 GB), schema-constrained,
   contamination-screened, including soft/ambiguous targets.
4. **Images** — the model accepts images (base64) in the `state`; training images are
   **generated by code** (charts, tables, diagrams, UI mockups, chess, floor plans,
   …) with programmatic ground-truth labels, so image decision supervision is exact.

The result should be a checkpoint that answers Kev-style `noul` / `choice` / `score`
questions about text **and images**, stays close to the base model on general
capabilities, and exposes the same TypeSafe-compatible `/v1/systemone` API.

## 2. Background

### 2.1 What Kev is (and what we reuse verbatim)

Kev is a family of small decision models (0.8B–27B, Qwen3.5/3.8) that never
generate text. Each checkpoint is a base LM + a rank-16 LoRA + a small **pointer
head**:

```text
<state> ...state...
<q> instructions <opt> option 1 </opt> <opt> option 2 </opt> ... <decide>
<q> instructions <opt> option 1 </opt> ... <decide>
```

- Each question is an isolated branch: it reads the state and itself, never other
  questions. `noul` = 2 options (no/yes), `choice` = K named options, `score` =
  ordered levels.
- The pointer head scores each option's `</opt>` hidden state against the
  question's `<decide>` hidden state; softmax gives the probabilities.
- Training is cross-entropy on the correct option, plus a fitted temperature for
  calibration (`head.pt["temperature"]`).
- Data: `decision-v7` — 12,576 train records / 15,576 questions built from ten
  public datasets + 896 generated policy examples + 1,680 rule-structure examples;
  frozen development (1,204) / calibration (968) / locked test partitions.
- Evaluation: accuracy, Brier, ECE, coverage@error, AURC, permutation and isolation
  checks (`kev.metrics`), frozen OOD suites (`transfer-v4`, `hard-v1`, `devtools-v1`,
  `documents-v1`, …), served at a temperature fitted on the model's own development
  rows.

We reuse: the record/API format, `decision-v7`, the pointer-head design, the label
semantics, `kev.metrics`, the calibration procedure, and Kev's experiment rules
(register arms before training; development partitions select; read test once;
paired record-clustered bootstraps; open-weight teachers only).

### 2.2 What DuplexCascade-Distill proved

In `duplex_cascade_distill/` a 4B model learned a new tag protocol without the
catastrophic forgetting that plain SFT caused. The mechanism:

> Teacher = the same weights with the adapters disabled (`model.disable_adapter()`),
> i.e. the frozen base model, read on the **same aligned sequence**. Student =
> base + QLoRA. Loss = supervised CE on the new tags at their positions **plus a
> forward-KL** (`CE(student_logits, softmax(teacher_logits/τ))`) on every content
> position, with the teacher's top-k (k=32) as the KL support.

Their M3 result on the same base (`eval/RESULTS.md`):

| Model | Function calling | General | Tag accuracy | KL drift |
|---|---|---|---|---|
| base | 100% | 100% | 0% | 0.51 |
| **distill** | **100%** | **100%** | **96.4%** | **1.07** |
| sft (no KL) | 55.6% | 41.7% | 98.0% | 4.76 |

Plain SFT collapsed function calling to 55.6%; the KL-anchored model kept it at
100% while learning the new protocol. Cost was ~1.4–1.6× SFT live, ~1.1× with an
offline teacher top-k cache.

**This project is the same idea applied to Kev's format**: the "tags" here are the
pointer head's answers; the "content" is the state and question text; the base's
knowledge is what we anchor.

### 2.3 What we change

| Axis | Kev | distill_jev |
|---|---|---|
| Backbone | Qwen3.5 / Qwen3.8 (text) | Gemma 4 E4B (text + vision; audio unused) |
| Modality | text | text **+ code-generated images (base64)** |
| Training stack | peft + `kev.train` + Modal | **Unsloth QLoRA** on the local RTX 4080 |
| Loss | pointer CE | pointer CE **+ frozen-base forward-KL + capability anchors** |
| Data | decision-v7 + programmatic policies | decision-v7 **+ Qwen3.5-9B synthetic + image decisions** |
| Serving | torch / MLX / fused CUDA | torch rows (+ optional prefix cache); GGUF only for qualitative checks (no pointer head in GGUF) |

## 3. Proposed method

### 3.1 Architecture

- **Base**: `unsloth/gemma-4-e4b-it-unsloth-bnb-4bit` (already in the HF cache at
  `/mnt/f/huggingface`; 4-bit NF4, 6.31 B params stored, ~10.8 GB on disk/GPU).
  Config facts that matter: text hidden 2560, 42 layers, sliding window 512 with
  full attention every 6th layer, tied embeddings, vocab 262,144, final logit
  softcap 30, vision tower 167 M, `vision_soft_tokens_per_image = 280`.
  *(Fallback if 16 GB is too tight after the M0 probe: `gemma-4-E2B-it`, also
  cached as GGUF.)*
- **Rejection candidate (garbage class, opt-in)**: the softmax runs over the `K`
  options **plus one extra logit**, `z_g = (g · q(h_decide)) * scale + g_bias`, a
  learned query-space direction with a bias initialised at −4 (≈1–2% of the mass).
  Because it reads only the `<decide>` state (which already attends to the state,
  the instruction and every option), it can raise itself when none of the options
  fits, is exactly permutation-invariant, and costs one dot product. Targets:
  hard label → one-hot over options, garbage 0; unanswerable record → garbage 1;
  ambiguous record → mass on both. At serving the `K` option probabilities are
  renormalized by `1 − p_garbage` and `p_garbage` is returned as a `none` field
  (Kev's calibration formulas then apply to the renormalized distribution).
  This is the fix for the documented failure mode "confidently wrong on records
  whose deciding evidence is missing" (Kev-9B answered 4% of unknowable rows with
  p ≥ 0.9; a rejection channel gives the model somewhere to put that mass).
- **Pointer head**: exact copy of `kev.model.PointerHead(d=2560, dp=256)` — two
  linear maps, dot product, softmax over options, temperature applied in eval mode.
- **Delimiters**: five of Gemma 4's reserved vocab slots (`<unused0>`..`<unused4>`,
  token ids 6..10) registered as additional special tokens. No vocabulary resize:
  M0 measured that adding new tokens transiently allocates +6 GB on the 2.8 B-row
  `embed_tokens_per_layer` table, past the 4080's headroom (Kev reuses Qwen's
  reserved tokens the same way). Each delimiter's 5 rows in `embed_tokens` and
  `embed_tokens_per_layer` get a trainable delta (`model/delimiters.EmbeddingDelta`);
  peft's `trainable_token_indices` merges the full tables on every forward
  (~8.3 GB transient), so it is not used. User text is escaped so option/branch
  delimiter tokens cannot be forged.
- **Encoding**: always the **row form** (one causal row per question = state +
  branch), never the packed block-causal mask. Gemma 4's sliding/global attention
  makes custom 4-D masks fragile; rows are exact by construction, match Kev's
  semantics (question isolation), and work on every backend. The state is
  recomputed per question in training — accepted, as in Kev.
- **Images**: an image in the state becomes `[<|image>] + 280 soft tokens`, then the
  text delimiters and question branches follow. Pointer positions are computed
  after the expansion. Image records always use one image, and the image is part of
  the state prefix (cached with it).

### 3.2 Loss

For a row with question `q` (options `o_1..o_K`, label `y`), teacher `T` = frozen
base (adapters disabled), student `S` = base + LoRA, `C` = the set of *content*
positions (state tokens + instruction tokens; image soft-token positions and option
span positions excluded):

```
L = CE_pointer(S, q, y)                                          # decision term
  + λ_kl  · (1/|C|) Σ_{t∈C} CE( S_logits_t , softmax(T_logits_t / τ) )   # knowledge term
  + λ_a   · (same, over every token of anchor rows)              # capability anchors
```

Notes:

- The knowledge term is the **forward KL** (student fits teacher), the variant that
  worked in DuplexCascade-Distill and is SDFT's practical recommendation.
- The teacher's support is its **top-k next tokens** (`k=32` default), so no
  `[T, 262144]` teacher logits are kept; the student's normaliser is `logsumexp`
  over the full vocabulary.
- `CE_pointer` is cross-entropy over the `K` option scores — `K+1` with the
  rejection candidate (3.1); when a record carries a soft `target`
  (ambiguous/unknowable records), it is cross-entropy against that distribution
  instead, as in Kev. Unanswerable records put their target mass on the garbage
  slot; a `--p_garbage` knob converts a fraction of the synthetic `none_pair`
  augmentations (the true option removed) into garbage targets, so the channel is
  trained even before the abstention data of 3.5 lands.
- Option spans are deliberately **not** in `C`: options are re-shuffled by the
  per-epoch augmentation, while state + instruction are augmentation-invariant —
  this is what makes the prefix cache exact (3.4).
- Suggested defaults: `λ_kl = 0.3`, `λ_a = 0.3`, `τ = 1.0`, `k = 32` (Duplex's
  smoke-tested values); all are CLI flags, the full λ/τ/k sweep is in §8
  (Ablations), and F1 in §4.4 decides the λ the full run ships.
- **Optional variants D3/D4**: D3 is a hidden-state anchor (feature matching at
  the positions the pointer head reads); D4 uses the frozen base's own zero-shot
  decision distribution as a soft pointer target. These are the two variants that
  most directly "leak" the base's knowledge into the Jev format; §4.3 defines
  both and §4.4 pre-registers the probes that decide whether they ship.

### 3.3 Why this should keep knowledge

The pointer head reads the base's hidden states; the LoRA that adapts them for the
decision format is exactly what erodes general ability. Anchoring the *next-token
distribution over everything but the decision positions* to the frozen base pins
the LoRA delta to ≈ 0 wherever the base is already correct (the DuplexCascade M3
table is the evidence that this works at 4B scale on the same 4080), and the
anchor rows extend the pinning to prompts that never appear in decision format.
§4 turns this claim into four measurable predictions and pre-registers the cheap
probes (F0–F5) that can falsify it before the full run.

### 3.4 The teacher: frozen 4-bit base, offline **prefix-level** top-k cache

Two ways to get teacher targets:

- **D1 (live)**: `with torch.no_grad(), model.disable_adapter(): teacher_logits = model(...)`
  — zero extra VRAM, one extra forward per step (~1.4–1.6× SFT). Used for smoke,
  validation and the equivalence check.
- **D2 (cached, default for full runs)**: because `C` = state + instruction, and
  neither option permutation, none/distractor augmentation nor epoch changes touch
  those tokens, the teacher targets for a row prefix can be computed **once** and
  cached:

  ```text
  key: (record_id, question_id)  ->  topk_ids[k], topk_logits[k] at the cacheable
  prefix (state + <|q|> + instruction + <|opt|>), plus a position mask
  ```

  Cache size for decision-v7 (≈16k rows × ≈450 prefix tokens × 32 × 6 B) ≈ 1.4 GB —
  small enough to keep on `/mnt/f`, and reusable across epochs, augmentations and
  arms. Training then costs a normal SFT step plus a gather + KL (~1.1–1.2×).

  For image records the prefix includes the 280 vision soft tokens; the cache
  stores the same shape and the mask excludes vision positions from the KL.

- **Teacher precision**: the teacher is the 4-bit base (the same weights the student
  starts from), so the anchor is "do not drift from what you actually are". If we
  later want true full-precision base distributions, the cache can be produced
  offline by a bf16/8-bit forward loop that never runs concurrently with training.
  Recorded in the cache provenance.
- **The cache is required, not just faster (M1 finding)**: Gemma 4 E-series shares
  KVs across layers, and Unsloth's gradient checkpointing cannot run **two forwards
  before one backward** (`CheckpointError: recomputed values ... different
  metadata`; the KV-sharing guard says so explicitly). Training therefore keeps
  exactly one forward + backward per micro-batch and reads the teacher from the
  cache. The live teacher (D1) stays available for short runs without GC, and for
  the M4 equivalence check. `enable_input_require_grads()` is called when GC is on
  (reentrant checkpointing is a silent no-op without it, because the frozen
  embedding tables give the first segment no grad-requiring input).

### 3.5 Data plan

**Text (core, reuse).** `evals/v7/decision-v7` train partition (12,576 records /
15,576 questions) from the Hub mirror `jaredpalmer/kev-suites@a88f56db` — the exact
data that trained Kev-0.8B/4B/9B's first stage. Records are re-filtered to the
Gemma tokenizer (`fits`), since token counts differ from Qwen's. Optional stage 2
delta data, mirroring what the current Kev-4B/0.8B added: `hard-v1` (programmatic,
regenerable), `devtools-v1`, `documents-v1` — all with their own eval partitions.

**Qwen3.5-9B synthetic (new).** Serve the cached GGUF with the local llama.cpp and
generate new TypeSafe-shaped decision records:

- no quantization step: `/mnt/f/GGUF/Qwen_3.5-9B/Qwen3.5-9B-UD-Q4_K_XL.gguf`
  (6.1 GB) fits the 4080 whole, with KV cache to spare
- serve: `~/llama.cpp/build/bin/llama-server
  -m /mnt/f/GGUF/Qwen_3.5-9B/Qwen3.5-9B-UD-Q4_K_XL.gguf
  --host 127.0.0.1 --port 8083 -c 32768 -np 4 --jinja`
  (llama.cpp build 10276 supports the `qwen35` architecture; the folder also ships
  `mmproj-BF16.gguf`, so the same server can optionally see the generated images —
  see M3)
- constrain with a JSON schema via `response_format={"type":"json_schema"}` /
  `-jf schema.json`, validate with the same pydantic model the trainer uses,
  retry on invalid output, dedupe on normalized state text, and screen every state
  against the frozen eval suites (exact normalized hash; same policy as
  `scripts/screen_overlap.py` in Kev).
- if the template emits reasoning blocks, disable them (`--chat-template-kwargs
  '{"enable_thinking": false}'`) or strip them; the schema constrains only the
  final JSON.
- families: new policy domains (health, legal, travel, HR, SaaS), new rule
  structures not in `decision-v7`'s train shapes, **soft/ambiguous targets**
  (sampling or a requested distribution → `"target"` over options, Kev finding 10),
  long documents, an optional **pt-BR** ticket family, and an **abstention family**
  (see below).
- alignment: Qwen3.5-9B is the model line Kev-9B's base belongs to, so its
  generations live in the same domain world as Kev's data, and it is open-weight
  (the training-label policy holds; never Jev, never closed models).
- volume: 2,000 records first (one overnight session), 5,000–10,000 total; every
  record carries provenance in `_meta` (generator, GGUF file, prompt hash, sampler).

**Images (new).** `data/images/generators.py` renders families with PIL/matplotlib
and returns `(image, spec)` where `spec` is the exact ground truth
(`{"family": "bar_chart", "values": [...], "max": 1, ...}`).
`build_image_records.py` turns each item into 2–5 questions across `noul` /
`choice` / `score` with programmatic labels, randomized option order, and optional
Qwen3.5-9B paraphrase of the instruction wording (it rephrases the generator's
spec, so labels stay exact; with `--mmproj` it can optionally look at the image,
but a label is never taken from the model).
Families for v1: bar/line/pie charts and trends, tables (which value/row), flow
diagrams (reachability), simple geometry and shape counts, UI mockups (primary
action), chess positions (legal move / better side, verified with python-chess),
gauges and needles, grids and heatmaps, rendered text (OCR-shaped questions),
comparison panels. Target 3,000–5,000 records, split by template/seed into
development and a frozen test set.
Storage: `state` is a list of content parts, images as base64 data URIs:

```json
{"state": [{"type": "text", "text": "Look at the chart."},
           {"type": "image", "base64": "data:image/png;base64,...."}],
 "questions": {"trend": {"type": "noul", "instructions": "Is the trend upward?", "label": true}}}
```

**Abstention / garbage records (new).** The rejection candidate needs examples whose
correct answer is "none of the options". Three programmatic sources come first,
because they need no generator: (a) synthetic `none_pair` records with the true
option removed (Kev's own augmentation; relabel the inserted none-option as
garbage); (b) the `hard-v1` missing-fact family, regenerated with its own builder
(its templates are train/dev/test split); (c) questions asked against states that
provably lack the evidence (drop the supporting sentence from a labelled record and
relabel as garbage). Qwen3.5-9B then widens the family: it writes questions about a
state whose answer is deliberately absent, and answers-excluded variants of its own
synthetic records. Target ≈10–15% of records carry some garbage mass; each keeps
its provenance. The gate is F6 (4.4): garbage mass high on unknowable rows, low on
knowledgeable ones, and answerable accuracy unchanged.

**Anchors (new).** 2,000–4,000 instruction prompts in the base's own chat template
(cached Alpaca-cleaned, function-calling examples from `function_calling_is_all_you_need/`
if licences allow, a reasoning slice, and image caption/VQA prompts). No pointer
loss, pure content-KL — the strongest anti-forgetting term per the DuplexCascade D2
result.

### 3.6 Serving

`serve/server.py` implements the TypeSafe-compatible API (same routes and response
shapes as `kev.serve`) on top of the merged model + `head.pt`:

- `POST /v1/systemone` (noul/choice/score), `GET /v1/models`;
- state content parts may include base64 images; questions stay text-only;
- rows are batched; the state prefix cache is reused across questions of the same
  request, as in Kev;
- the fitted temperature from `head.pt` is applied to all `K+1` logits in eval
  mode; the option probabilities are renormalized by `1 − p_garbage`, the answer
  and confidence formulas run on the renormalized distribution unchanged, and the
  rejection mass is returned as an extra `none` field on every answer (a
  documented extension; strict clients ignore unknown fields). A `none`-threshold
  is how a caller automates the confident decisions and routes the rest to a
  human — the exact use case the Kev family is for;
- GGUF export is **optional and qualitative only**: llama.cpp supports the
  `gemma4` architecture (build 10276), and the merged model + mmproj can be
  converted for generation checks (`llama-mtmd-cli`), but the pointer head has no
  GGUF representation, so the decision API is torch-only.

## 4. Feasibility of the "knowledge leak" (analysis and pre-registered probes)

The distillation term is the reason this is not just another QLoRA. This section
states what the leak can and cannot do, and the cheap experiments that decide
whether the mechanism earns its ~15% step-time cost **before** the full run.

### 4.1 Four claims hiding behind "leak" (and one new capability)

| Claim | Mechanism | Existing evidence | Expected size | Test |
|---|---|---|---|---|
| (a) **Retention** — the student does not lose what the base knows | forward-KL toward the frozen base constrains every content-token distribution | duplex M3: function calling 55.6% (plain SFT) vs **100%** (KL); drift 4.76 vs 1.07 | tens of pp on capability probes | F1, F2 |
| (b) **Readout** — the head learns to *use* knowledge already in the base | knowledge lives in hidden states; the pointer head is the tap; KL keeps the tap aligned | Kev: MMLU-Pro 0.545 trained vs 0.540 base; knowledge MCQ (ARC/OBQA/CSQA) is trainable for the same reason | decision-accuracy floor, not a gain | F0 |
| (c) **Transfer** — better answers on questions whose labels were never seen | soft teacher distributions carry uncertainty/ranking a hard label does not | Kev finding 10: soft targets +1.1 pp accuracy, −0.011 Brier; KD/SDFT literature | 0.5–2 pp, not new capabilities | F1, F2 (α-sweep) |
| (d) **External leak** — a stronger Jev-like teacher | decision distributions from Kev-9B (same format, calibrated) as soft targets | none yet | unknown; potentially the largest | F5 (phase 2) |
| (e) **Abstention** — honest "none of these fit" | one extra rejection logit trained on unanswerable records | Kev: unknowable training made models honest; M0: routing verified on real features | large on unknowable panels, ≈0 on knowable rows | F6 |

The information-theoretic bound is worth stating plainly: **a KL to the teacher
cannot create answer information the teacher does not have.** It can (i) preserve
information, (ii) transfer the teacher's uncertainty and ranking, and
(iii) stabilise optimisation. Everything the model knows at the end is what the
frozen base's hidden states expose plus what the labels add. Kev's finding that
knowledge is set by the base (MMLU-Pro ≈ base at every size) is the same
statement from the other direction.

### 4.2 What each loss term actually touches

- The token-KL constrains the LM's conditional distribution on state/instruction
  tokens. Since Gemma's embeddings are tied, this strongly constrains hidden
  states — but it is **not** a constraint on the specific `</opt>` and `<decide>`
  subspaces the pointer head reads: those are new tokens with trainable
  embeddings, and the option spans are augmentation-variant, so token-KL only
  anchors them indirectly.
- The pointer CE only sees the label (or a `target`); it is the only term that
  teaches the decision task.
- The image is fused before the text positions the KL sees, so the KL constrains
  the vision tower/projector only through their effect on text logits. With a
  frozen vision tower, how much visual evidence reaches the head is an empirical
  question (F4).
- Prediction this analysis makes: retention is reliable (4.1a), readout is
  measurable (F0), transfer needs soft targets (D4), and the readout positions
  themselves are best protected by a **hidden-state anchor** (D3), not only by
  token-KL.

### 4.3 Design changes this analysis implies

1. **D3 — hidden-state anchor at readout positions (new default candidate).**
   Reuse the teacher forward and add a feature term at the positions the head
   reads (`</opt>` and `<decide>` hidden states): cosine distance (scale-free)
   plus an optional MSE term with weight `λ_h`. This directly pins the geometry
   the pointer head consumes, which token-KL does only indirectly. Because option
   order varies per epoch, these positions are *not* augmentation-invariant:
   compute the anchor **live** on a fraction of steps (e.g. every 4th), while the
   content-position KL stays on the cache.
2. **D4 — base decision targets (decision-level leak).** For each training
   question, ask the frozen base to decide in a generative frame (append the
   option list plus a short `Answer: (` suffix and read the next-token logits at
   the option-name first tokens) to get `q_base(o)` over the same options. Use it
   as a soft pointer target, `target = (1 − α)·onehot(label) + α·normalise(q_base)`,
   only when the base is confident enough (e.g. max ≥ 0.6) or after a temperature.
   Cache size is trivial (K floats per question), it works on unlabelled states
   too, and it is the variant that most directly leaks the base's decision
   preferences into the Jev format. α = 0 is the current recipe; α and the
   confidence threshold are the sweep.
3. **D5 — external decision teacher (phase 2).** Kev-9B's served distribution per
   question, used exactly like D4. Feasibility caveat: Kev-9B is bf16-only and
   does not fit the 4080 (≈18 GB); it runs on Modal (the existing
   `kev/modal_app.py`) or a rented GPU, or as a 4-bit merged model whose parity
   would need checking. Costed separately, only after the cheaper probes pass.
4. **Vision path** — decide projector training / vision LoRA from F4, not by
   default.

### 4.4 Pre-registered probes (cheap first, all before the full run)

**F0 — frozen-feature head probe (hours, text).**
Precompute the frozen 4-bit base's hidden states for decision-v7 train rows (one
row per question, exact final encoding), train **only** the pointer head on the
cached features (minutes), score the development partition. This measures the
"free leak ceiling": how much Jev-format accuracy the frozen base already exposes
through the head, before any LoRA, and it fixes the head-only floor for every arm
that follows.
*Gate*: report accuracy/Brier per question type; if it is at chance, the base's
knowledge is not directly readable through this head and the readout claim (4.1b)
is false for this architecture (the main recipe still adapts the backbone).

**F1 — drift/decision Pareto over λ (one night).**
Four arms, identical data and schedule, 2,000 steps each: λ ∈ {0 (plain QLoRA
SFT), 0.1, 0.3, 1.0}; then τ ∈ {1, 2} for the winner. Per-step held-out monitors:
mean per-token KL(student ∥ base) on a fixed general + decision mix (the
DuplexCascade metric), function-calling exact match, a general-QA slice, then
development decision accuracy/Brier at the end.
*Gate*: pick the λ that maximises development decision accuracy subject to
drift ≤ SFT drift / 3 and capability probes within noise of the base. If **every**
λ > 0 costs more than 2 pp decision accuracy even after τ/k tuning, the KL is
mis-specified (positions, τ, k) and the full run does not start until it is fixed.

**F2 — knowledge readout and where drift happens (hours, eval-only).**
A held-out panel of MMLU/ARC-style questions converted to the pointer format
(eval-only, never trained), scored with the F1 arms and with the base's own
zero-shot prompt baseline. Plus per-position drift on held-out records:
knowledge-bearing sentences vs distractor text vs option spans. Prediction: the
KL arm's drift concentrates where training changed the format (options,
delimiters) and stays ≈ 0 where the evidence is.
*Gate*: the KL arm's knowledge probes are no worse than the base and better than
the SFT arm; otherwise the anchor is not doing what it is supposed to.

**F6 — abstention / garbage channel (hours, eval-only; mechanics already probed).**
Train two heads on the same recipe, with and without the rejection candidate, and
score the held-out abstention panel built in 3.5 (synthetic removed-evidence rows,
`hard-v1` missing-fact dev, `transfer-v9` unknowable items) plus a knowable control
slice. Metrics: mean `p_none`, share of unknowable rows answered at ≥0.9 confidence
(Kev's `unknowable_report`), coverage at a 5% error budget, and accuracy/Brier on
the knowable slice.
*Gate*: `p_none` on unknowable rows is high (suggest mean ≥ 0.5), the ≥0.9
confident-wrong share drops versus the no-garbage head, and knowable slice
accuracy/Brier are within 1 pp / 0.01 of the no-garbage head. M0 already verified
the mechanics on the real model (5.5), so F6 measures quality, not plumbing.

Pre-registered reading order: **garbage-free head answers the panel first and its
thresholds are recorded before the garbage head is trained**, so the F6 comparison
is paired and not a post-hoc rescue.

**F3 — teacher fidelity (1 h).**
Exact logits-path parity in M0 (softcap 30, tied embeddings, vision fusion);
measured top-32 teacher mass per content position; a 4-bit-vs-bf16 teacher
comparison on 200 rows (bf16 loaded once, sequentially).
*Gate*: mean top-32 mass ≥ 0.9 (else raise k), and the 4-bit teacher's per-token
KL to the bf16 teacher is small relative to the training drift it is meant to
prevent (report; otherwise move the cache to an 8-bit/bf16 offline run).

**F4 — vision leak (half a day).**
Same cached-feature trick on image records (frozen vision + text states), head
trained on features: measures what the frozen base sees in code-generated images.
Then arms: frozen vision / trainable projector / vision LoRA, with a per-family
breakdown (charts, tables, diagrams, UI, chess).
*Gate*: frozen-vision head-only must beat the majority class by a pre-set margin
(suggest +20 pp); if not, projector/vision training is required and budgeted; if
still not, images ship as v2 and the text model proceeds unchanged.

**F5 — external teacher (phase 2, Modal or a rented GPU).**
Kev-9B soft targets (D5) on the F1-winning recipe; paired record-clustered
bootstrap on decision dev + transfer-v4 against the D4-only model. The registered
read decides; report even if negative.

### 4.5 Go/no-go for the full run

Proceed when: F1 selects a λ with drift reduced ≥ 3× versus SFT and decision
accuracy within 1 pp of SFT; F0 and F4 are above chance; F2 shows the KL arm
retaining knowledge; F3 is within bounds. A failed gate sends the recipe back to
tuning (positions, τ, k, λ). If the KL still buys nothing after that, the
fallback is plain QLoRA + anchor rows — which is exactly the SFT arm already
measured. That is a valid, reportable outcome too: it would say the
Kev/Gemma combination does not reproduce the DuplexCascade retention effect at
this scale.

### 5.2 Memory budget (the tightest constraint)

The 4-bit checkpoint is 10.8 GB (6.31 B params; vision/audio towers and per-layer
embeddings stay unquantized), leaving ~5 GB on the 4080. The plan:

- `load_in_4bit=True`, `dtype=bf16`, `use_gradient_checkpointing="unsloth"`,
  `max_seq_length=2048`, per-device batch 1, grad-accum 16.
- Freeze the audio tower if the loader allows it (not needed; ~0.6 GB), keep the
  vision tower frozen in v1 (167 M), train the projector only if the M0 probe shows
  the head cannot learn image records without it.
- Fallbacks if OOM: `max_seq_length` 1536 → 1024, single image per state, state cap
  256 tokens for image records, `optim="adamw_8bit"`, shorter branches.

### 5.5 M0/M1 findings (2026-09-24/25, probes and smoke passed)

`tools/probe_m0.py` → `runs/probe_m0.json`, all checks green:

- **Load**: `unsloth/gemma-4-e4b-it-unsloth-bnb-4bit` in 82 s from the local cache;
  10.97 GB allocated, 4.59 GB free on the 4080. Top level is
  `Gemma4ForConditionalGeneration(model=Gemma4Model(language_model=Gemma4TextModel), lm_head)`.
- **Delimiters**: `<unused0>`..`<unused4>` are ids 6..10 and tokenize as single
  tokens once registered as additional special tokens; vocab stays 262144. The
  `EmbeddingDelta` wrappers hold the only delimiter parameters (5×2560 and
  5×10752 = 66 k), and they must be un-frozen after `get_peft_model`
  (`prepare_model_for_kbit_training` freezes everything it does not know).
- **Readout**: `output_hidden_states=True` returns the fused text hidden states
  (`hidden_states[-1]`; there is no `last_hidden_state` on the LM output), and
  `logits_to_keep` accepts an **index tensor**, so the KL can compute logits only
  at the content positions instead of full-vocab `[T, 262144]` tensors.
- **Training**: pointer-head CE + backward reaches all 4 head parameters and 260
  LoRA/delta gradient tensors; `model.disable_adapter()` on the unsloth PeftModel
  returns a different (frozen-base) distribution, so the teacher path is live.
- **Images**: a 224 px image expands to `boi + 256 soft tokens + eoi` (n is
  image-dependent), and the delimiters keep their order in the expanded row;
  hidden states are `[280, 2560]`. The pointer positions are found by scanning
  token ids in the expanded sequence.
- **Peak VRAM 12.35 GB** (gate < 15.5 GB) after text forward + backward + image
  forward at seq 280. The one pitfall that mattered: peft's
  `trainable_token_indices` rebuilds both embedding tables per forward
  (19.7 GB peak, spilling to host memory in WSL); the per-row delta wrapper is
  what makes the budget work.
- **M1 training works with the offline teacher cache and gradient
  checkpointing**: one forward + backward per micro-batch, 0.83 s at the prepared
  distribution (p50 107 tokens), 500 steps in 54.7 min, no OOM. Loss 2.42 → 0.65,
  pointer CE from 5–7 to 0.0003–0.3 (chance is ~1.1–1.6), KL steady at 0.7–1.7,
  and the garbage channel routes: `p_garbage` ≈ 1.0 on the smoke's unanswerable
  rows vs ≈ 0.0002–0.02 on answerable ones.
- **M1 dev read** (`eval/eval_decisions.py`, decision-v7 development, 1,468
  questions): **accuracy 0.798**, Brier 0.290, ECE 0.104, coverage@5% error
  0.579, mean `p_none` 0.019 — after 500 steps on 2,000 rows (a sixth of
  decision-v7's train partition), against Kev-4B's 0.873 trained-source number
  from two full epochs. Checkpoint: `runs/smoke`; report:
  `runs/smoke-eval/report.json`.
- **M6 retention read** (base vs trained chat, trained pointer; report
  `docs/m6-retention.md`): chat is level with the base (HellaSwag acc_norm 0.589→0.597,
  ARC 0.406→0.400, MMLU 0.322→**0.389**, TruthfulQA MC2 0.372→0.368), while the pointer
  head on the same tasks scores HellaSwag **0.752**, ARC **0.856**, MMLU **0.657** — the
  system_one readout taps far more of the backbone's knowledge than chat continuation
  scoring, at ~0.13 s/question against ~0.77 s/example. Drift on 200 Alpaca prompts:
  mean KL 1.864, 88.4% argmax agreement (no control arm yet).
- **M5 full run** (15,576 rows, 2 epochs, 8.5 h): dev **0.860** acc / raw Brier
  0.227 / raw ECE 0.079, served at T=1.625 Brier 0.212 / ECE 0.037 /
  coverage@5% 0.722; transfer-v4 dev **0.751** / raw 0.360 / served 0.323 /
  ECE 0.076. Out-of-fold calibration ECE 0.016, separated. Trained-source
  accuracy is at the Kev-4B level for a single recipe stage; new-source accuracy
  sits between Kev-0.8B and Kev-4B (report-only comparison). Full report:
  `docs/m5-text-run.md`.
- **Garbage candidate works on real features**: with the frozen hidden states of
  a knowable row ("sky is blue") and a nonsense row (options "purple"/"orange"),
  a fresh `PointerHead(garbage=True)` trained 300 steps routes the mass exactly —
  knowable → `[1.0, 0.0, 0.00]`, nonsense → `[0.0, 0.0, 1.0]`, with gradients on
  `g` and `g_bias` and `p_garbage = 0.007` at init. The standalone synthetic probe
  (`tools/probe_garbage.py`, `runs/probe_garbage.json`) passes all five checks:
  init ≈ 0.5% garbage, routing, answerable accuracy 100%, gradient flow, and exact
  permutation invariance.

## 8. Evaluation protocol

Following Kev's standing rules: register the arms and the decision rule **before**
training; development partitions select; test partitions are read once per
candidate; paired record-clustered bootstrap intervals; served at the temperature
fitted on the model's own development rows; report negative results too.

- **Decision quality (text)**: `decision-v7` development (1,204 records), then
  `transfer-v4` (656 development / locked test) for new-source behaviour.
  Metrics: accuracy, Brier, ECE, coverage@5% error, AURC, per question type
  (`data/metrics.py`).
- **Decision quality (images)**: `evals/image-decisions-v1` — development selects,
  test read once; per-family accuracy/Brier; templates and seeds held out from
  training.
- **Abstention (the garbage channel, F6)**: the held-out abstention panel of 3.5
  (`unknowable_report`-style: mean `p_none`, share of unknowable rows answered at
  ≥0.9, confidence drop vs intact controls) plus coverage at a 5% error budget and
  accuracy/Brier on a knowable control slice, comparing the garbage and
  garbage-free heads on identical rows. Kev's finding that training on unknowable
  records made the model honest is the precedent; this measures whether an explicit
  rejection candidate does it better.
- **Knowledge retention**: (a) mean per-token KL(student ∥ frozen base) on a
  held-out mix of decision + general + image prompts (the direct SDFT metric);
  (b) function calling exact-match on a fixed set; (c) lm-eval subset
  (HellaSwag / ARC / MMLU) merged-model before/after; (d) a small vision
  caption/VQA slice with generation, before/after.
- **Comparison table** (the deliverable): base Gemma-4-E4B (zero-shot prompt
  baseline on the same questions), plain QLoRA SFT (no KL), **distill_jev
  (this method)**, and published Kev-9B/4B numbers as a reference (different base
  and tokenizer — report-only, not a paired comparison).
- **Ablations**: λ ∈ {0, 0.1, 0.3, 1.0} (λ=0 is the SFT control), τ ∈ {1,2},
  k ∈ {16,32,64}, live vs cached teacher, images on/off, anchors on/off,
  soft-target on/off, optional vision LoRA.
- **Contamination**: every synthetic and image state is checked against the test
  partitions of every frozen suite (exact normalized text hash), and the image
  suite's generator templates are excluded from training.

## 9. Risks and open questions

1. **VRAM** (highest): 10.8 GB of weights on a 16 GB card. Mitigations in 5.2;
   if none is enough, fall back to E2B (cached GGUF) or train at seq 1024.
2. **Multimodal plumbing**: image expansion, pointer position bookkeeping,
   `mm_token_type_ids`, hidden-state and logits access through Unsloth's patched
   forwards. M0 exists to fail cheaply here.
3. **4-bit teacher**: the anchor is the quantized base (the model the student
   literally starts from), not the bf16 release. Acceptable for anti-forgetting;
   a bf16/8-bit offline cache is the fallback if retention evals disappoint.
4. **Forgetting may still exceed DuplexCascade's**: we add 5 tokens, resized
   embeddings, a new head and a much narrower task than chat. The anchors and the
   retention panel are the guard; acceptance thresholds are set at M5 before the
   test read.
5. **Qwen3.5-9B throughput** (9B Q4 fully offloaded on one 4080): generation
   volume is the schedule risk. Mitigate with `-np 4`, short outputs, and a
   2k-record first batch that is enough for the smoke path.
6. **Image questions are synthetic-only**: the model learns code-generated
   imagery; real photos may transfer poorly. Stated as a limitation; the eval suite
   is synthetic by design and the frozen generators include held-out families.
7. **GGUF cannot carry the pointer head**: serving stays torch; GGUF is only a
   qualitative generation check. Don't promise a llama.cpp decision endpoint.
8. **Licences**: Apache-2.0 for the base (Gemma 4 E4B IT) and derivatives; each dataset's
   licence (the released weights and model card are at `lumierenoir/klev-e4b`).
9. **Augmentation/cache coupling**: KL must stay on augmentation-invariant
   positions or the cache is wrong. M4's equivalence test is the guard, and the
   encoder pins `C` to state + instruction.
10. **One GPU**: generator serving and training cannot overlap; the plan is
    sequential sessions.

## 10. Open decisions (need your call)

1. **Name/size**: keep `distill_jev` as the repo and call the checkpoint
   `distill_jev-4b` (Gemma 4 E4B), or another name?
2. **Base**: `gemma-4-e4b-it` (cached, instruction-tuned, knowledge worth keeping)
   vs a non-instruct pretrained release if one exists. Default: the `it` 4-bit.
3. **Images**: confirm the families list and the mix ratio (default ~20–25% of
   records); decide whether option descriptions may ever contain images (default
   no).
4. **pt-BR**: include a Portuguese synthetic family (Kev has none)?
5. **Phase 2 distill head (D5/F5)**: add soft-target distillation from a stronger
   Jev-like teacher (e.g. `jaredpalmer/kev-9b` distributions) into the pointer
   head, in addition to hard labels and the D4 base targets? (Extra download +
   inference; doesn't fit the 4080 in bf16 — Modal or a rented GPU.)
6. **Epochs**: one epoch first (cheaper) and extend as a delta, or go straight to
   Kev's two-epoch recipe?
7. **Synthetic volume** (Qwen3.5-9B): 2k records first or a bigger overnight run (5–10k)?
8. **Garbage candidate**: learned query direction + bias (shipped default, probed
   in M0) vs a contextual garbage slot (`<unused5>` appended after the options,
   more expressive but order-dependent) vs both. And whether the `none` field is
   exposed always or behind a `?ext=none` request flag.
9. **Abstention mix**: how much of each training epoch should be unanswerable
   records (suggest 10–15% total garbage mass), and whether the eval-time
   `p_none` threshold should be fitted like the temperature.
