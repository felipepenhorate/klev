# M11 — klev on Qwen3.5-0.8B, and the ROCm environment it needed

Date: 2026-09-27
Branch: `gemma4-e2b-qat` (the Qwen arm lives here too; see "Branching" below)
Goal: rerun klev on `Qwen/Qwen3.5-0.8B` to compare against the Gemma 4 E4B main run.

## Verdict

**It works, on the RX 6600M.** Unlike the Gemma 4 arms, Qwen3.5-0.8B has no PLE embedding
table, so it trains in 0.89 GB of 4-bit weights and 1.39 GB peak. A full 2-epoch
decision-v7 run — the same 3,894 steps the E4B run took 8.5 h for on a 4080 — fits in an 8 GB
laptop card.

| | Gemma 4 E4B (reference) | Gemma 4 E2B QAT | **Qwen3.5-0.8B** |
|---|---|---|---|
| total / activated | — | 5.10B / ~2B | ~0.8B dense |
| hidden / layers | 2560 / — | 1536 / 35 | 1024 / 24 |
| vocab | 262,144 | 262,144 | 248,320 |
| `embed_tokens_per_layer` | 262144 × wide (fp16, never quantized) | [262144, 8960] = 4.70 GB | **absent** |
| tied embeddings | yes | yes | yes |
| `final_logit_softcapping` | 30.0 | 30.0 | **none** |
| weights in 4-bit | — | needs ≥12 GB, OOMs at 7.73 GB here | 0.89 GB |
| trains on 8 GB? | no | **no** | **yes** |

## What had to change in the code

Three real porting changes; the rest of klev is reused verbatim.

1. **Delimiters** (`data/config.py`). Qwen has no `<unusedN>` slots, so the delimiters are
   five of Qwen's own reserved tokens — `<|fim_prefix|>`, `<|fim_suffix|>`, `<|fim_middle|>`,
   `<|fim_pad|>`, `<|repo_name|>` (ids 248060–248064); `<|file_sep|>` is left alone. These
   are exactly the "`<|fim_prefix|>`-style reserved tokens" that `data/config.py` already
   said Kev reuses, so this arm is closer to klev's lineage than the Gemma arms were. They
   exist in the vocabulary, so no resize and only 5 embedding rows are trained.

2. **No BOS** (`data/encoding.py`). `tokenizer.convert_tokens_to_ids("<bos>")` returns `None`
   on Qwen (`bos_token_id is None`) rather than raising, which silently corrupted the
   state-length arithmetic (`state_tokens = pos["q"][0] - 2`). Now the tokenizer's own
   `bos_token_id` is prepended only when it exists, and the arithmetic accounts for it.

3. **`logits_to_keep=1`** (all three entry points). Nothing in klev reads `out.logits` — the
   pointer readout and the KL both work off `hidden_states[-1]` and gather their own vocab
   logits in chunks — but transformers projects *every* position through `lm_head` by
   default. That is 248,320 × seq_len of dead tensor: 1.07 GB at seq 2048, and the single
   largest allocation in the step.

Verified byte-compatible: the full prep produces **15,576 rows / 506 garbage rows**, exactly
the E4B run's `15,576 rows, 506 garbage rows (3.2%)`.

## The ROCm environment (four separate problems)

The reference recipe is `Projects/Qwen_3_(0_6B)_Text.ipynb`, now captured in
`scripts/rocm_env.sh`. Each of these was load-bearing, and three of them were invisible.

### 1. bitsandbytes was too old, silently disabling 4-bit

unsloth gates on `bnb.__version__ > 0.48.2.dev0` (`unsloth/device_type.py:195`). The build in
`Projects/Commands.txt` was **0.48.0.dev0**, so unsloth printed
"`bitsandbytes` is unavailable here - disabling 4bit/8bit" and quietly loaded 16-bit.
No ROCm wheels exist on PyPI, so it has to be built:

```bash
git clone --recurse https://github.com/bitsandbytes-foundation/bitsandbytes.git
cmake -DCOMPUTE_BACKEND=hip -DBNB_ROCM_ARCH=gfx1030 -S . -B build
cmake --build build -j8 && pip install --no-deps .
```

`main` is 0.50.3.dev0. `gfx1030` is in the default HIP arch list and is what
`HSA_OVERRIDE_GFX_VERSION=10.3.0` targets. Verified: `Linear4bit` fwd+bwd finite,
`quant_state` present, **blocksize 64**, `AdamW8bit` steps, and unsloth's
`ALLOW_BITSANDBYTES` / `ALLOW_PREQUANTIZED_MODELS` both flip to `True`. Since 0.49.0
prequantized 64-blockwise is supported on Radeon (Navi) and since 0.49.2 on CDNA too, so
this arch is explicitly covered. Build takes ~45 s for a single arch.

### 2. `UNSLOTH_COMPILE_DISABLE=1` — the actual training blocker

With unsloth's compile wrapper on, a **16-token forward took minutes at 0% GPU
utilization**, almost entirely CPU. With it off: 0.107 s at seq 256. This single variable
was the difference between "impossible" and "2 hours", and it appears only in the notebook.

### 3. `torch.cuda.is_bf16_supported()` is not trustworthy under unsloth

Importing unsloth **replaces** that function (`unsloth/__init__.py:507`,
`unsloth/_gpu_init.py:415-431`), and on this box the replacement reports `False` for consumer
Navi. So any `compute_dtype()` keyed on it silently returns fp16 in every real run — the
first bf16 attempt reported `compute dtype torch.float16` and produced losses bit-identical
to the fp16 run.

The claim in `unsloth-fix.sh` that gfx1032 "lacks the bf16 fdot2 instruction" is true only of
**Triton**. Measured directly, native bf16 matmul + backward is finite and correct. The
supported knob is `TORCH_ROCM_AOTRITON_ENABLE_BF16=0`, not lying to torch. `model/load.py`
now takes `KLEV_DTYPE` as an explicit override for this reason.

Note bf16 remains unusable end-to-end here for a different reason: accelerate independently
consults the same (patched) probe and refuses with "You need Ampere+ GPU with cuda>=11.0".

### 4. fp16 specifics

- **GradScaler needs fp32 trainable params.** The delimiter embedding deltas were created as
  `dtype=base.weight.dtype`, i.e. fp16, and training died on step 0 with
  `ValueError: Attempting to unscale FP16 gradients.` The E4B reference never hit this
  because bf16 uses no scaler. Deltas are now fp32 (5 rows, free) plus an in-place upcast
  safety net in `build_model` — in place, because `setattr`-ing a new Parameter would leave
  the `deltas` dict pointing at orphans and `head.pt` would save zeros.
- **The first ~6 steps report `grad_norm: nan`.** That is GradScaler calibration, not a
  failure: the initial scale 65536 overflows, those steps are skipped, and by step 6 the norm
  is finite (303.7) and the step applies.
- **`qwen3_5` and `gemma4` are in unsloth's `FORCE_FLOAT32` list** — plain fp16 NaNs the
  grad_norm in the *backward* for these two families. `UNSLOTH_FORCE_FLOAT32=1` makes unsloth
  load bf16 weights, compute matmuls in fp16 and hold the residual stream in float32. It must
  stay unset for Qwen3.

## Two silent fallbacks worth knowing about

- **`optim="adamw_8bit"` resolves to plain `AdamW`.** `adamw_8bit` is still a valid alias in
  transformers 5.6.2, but the created optimizer is `torch.optim.AdamW` with two param groups.
  Harmless at 6.9 M trainable params (55 MB of fp32 state), but it is not the 8-bit optimizer
  the config names.
- **`linear_attention` layers are on a torch fallback.** Qwen3.5-0.8B is 18 gated-deltanet /
  6 full-attention layers (`full_attention_interval=4`, `linear_conv_kernel_dim=4`,
  `mamba_ssm_dtype=float32`). `flash-linear-attention` is needed for the fast path; it is
  split across two PyPI packages (`flash-linear-attention` ships `fla/layers` + `fla/models`,
  `fla-core` ships `fla/ops` and `fla/modules`) and both were installed here. `causal-conv1d`
  is still absent, so the short conv uses a torch fallback. The first backward pays a
  **595 s** one-time Triton autotune (then cached in `~/.triton/cache`); warm steps are
  0.369 s fwd+bwd+optimizer at seq 256.

## Recipe deviation from the E4B main run

`--lr-scheduler-type linear` instead of `cosine`. On transformers 5.6.2 the Trainer fast loop
pins the LR at exactly 0 for every step when the scheduler is `cosine` and
`warmup_steps > 0` — verified at 6 steps with `warmup 50`, all reporting
`learning_rate: 0`, where 1.2e-05 is correct. `get_scheduler("cosine", ...)` itself is fine
when called directly, and `linear` ramps correctly, so this is a bug workaround rather than a
choice. It is now a CLI flag.
